## 3. 根因分析

### 3.1 为什么 fast_retrans=0？（**P0 问题**）

快速重传流程：
1. 接收方收到乱序数据 → 发送 dup ACK
2. 发送方收到 dup ACK → `parse_fastack()` 增加 `seg.fastack`
3. 当 `fastack >= fastresend (默认2)` → 触发 fast retransmit

**问题定位**: SNMP 显示 `retrans=889` 但 `fast_retrans=0`，说明：
- 要么 ACK 没有正确发送/接收
- 要么 `parse_fastack` 没有被调用
- 要么 `fastresend` 配置未生效

### 3.2 为什么 Tokio 比 Smol 重传多 8.5x？

| 因素 | Tokio | Smol |
|------|-------|------|
| 线程数 | N (多核) | 2 |
| 调度策略 | work-steal | 协作式 |
| 跨线程唤醒 | 有（notify_parked_local） | 无 |
| ACK flush 延迟 | 可能更高（竞争） | 更低 |

**假设**: tokio 的多线程调度导致 ACK 发送延迟更高，产生更多 RTO 超时。

### 3.3 为什么 P999 抖动大（max >> P999）？

在 macOS 上，max 达到 187ms 远超 P999 的 78ms，说明：
- 少数请求经历了极端的 RTO 级联
- macOS timer coalescing 引入额外 1-5ms 抖动
- 可能存在任务饥饿（某个 worker thread 长时间未调度）

## 4. 优化方案

### 方案 1: 修复 Fast Retransmit（**P0，最高优先级**）

**目标**: 让 `fast_retrans > 0`，减少 RTO 超时

**步骤**:
1. 添加 debug 日志验证 `parse_fastack` 是否被调用
2. 检查 `ack_push` 是否正确将 ACK 加入 acklist
3. 检查 `flush_with_current(flush_acks=true)` 是否正确发送 ACK
4. 验证 `fastresend` 参数是否正确设置（`set_nodelay(1, 10, 2, 1)` 应设 fastresend=2）

**预期效果**: P999 降低 60-80%（从 RTO 200ms+ 降至 RTT 级别 ~1ms）

### 方案 2: 减少 Tokio 跨线程唤醒（**P1**）

**目标**: 降低 tokio 调度延迟

**方法**:
- 使用 `current-thread` runtime（单线程调度器）
- 或设置 task affinity 让 KcpConn 的 input/flush 在同一线程

**预期效果**: P99 降低 30-50%

### 方案 3: ACK 发送优化（**P1**）

**目标**: 确保 ACK 及时发送，减少 dup ACK 延迟

**方法**:
- 检查 `acklist` 的 flush 时机
- 考虑 `ack_no_delay=true` 时的立即 flush

**预期效果**: 减少重传次数 50%+

### 方案 4: macOS UDP 优化（**P2**）

**目标**: 减少 syscall 开销

**方法**:
- 增大 socket buffer（SO_RCVBUF/SO_SNDBUF）
- 考虑使用 `sendfile`/`splice`（Linux）

**预期效果**: 吞吐提升 5-10%
